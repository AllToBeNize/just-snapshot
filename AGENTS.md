# Repository Rules

Guide for AI coding agents working on just-snapshot (renamed from Snapshot in 0.4.0). The user-facing feature overview lives in `README.md`; the architecture rationale lives in `docs/technical-plan.md`.

## Project Overview

just-snapshot is a Windows 10/11 x64 screenshot tool written in Rust on raw Win32 (`windows` / `windows-sys` crates, GDI drawing, no UI framework). It idles in the tray with a blocking message loop; every capture buffer, GPU resource, and helper thread is created per capture session and released afterwards. Keep idle CPU, wake-ups, and memory at zero growth.

UI strings, error messages, and user-facing docs are Simplified Chinese. Code, identifiers, and comments are English.

## Build and Test

Build and test on Windows only. `snapshot.ps1` locates Cargo and the Visual Studio developer environment itself.

| Command | Purpose |
| --- | --- |
| `.\snapshot.ps1 build` | Release build: `target/x86_64-pc-windows-msvc/release/just-snapshot.exe` |
| `.\snapshot.ps1 test` | Run all unit tests (`test`, `package` and `release` run them on a desktop of their own, `Invoke-OnHiddenDesktop`: they open real overlays and pins, which would flash on the user's screen when releasing from the desktop session) |
| `.\snapshot.ps1 package` | Test, build, then write `dist/just-snapshot-v<version>-windows-x64.zip`, `dist/just-snapshot-v<version>-setup.exe` and a `.sha256` for each |
| `.\snapshot.ps1 release -Tag vX.Y.Z` | Package and create a draft GitHub Release (needs `gh auth login`) |

- The script writes rustup progress to stderr. In a remote or non-interactive PowerShell session that is turned into a terminating error; run it from `cmd` instead (`powershell -NoProfile -ExecutionPolicy Bypass -File snapshot.ps1 test > log 2>&1`).
- Run `.\snapshot.ps1 test` before reporting a change as done. The build must stay warning-free.
- A running `just-snapshot.exe` locks the release binary; exit it from the tray before rebuilding.
- UI previews without a desktop session: run the test binary in `target/x86_64-pc-windows-msvc/release/deps/snapshot-*.exe` with `preview --ignored`. It renders the settings window (every theme and main states), the toolbar and option bar in every theme, the dialog, the text frame and the tray icons to `%TEMP%\snapshot-preview\*.png`. Look at them after any UI change.
- Long capture that does not stitch: create `%LOCALAPPDATA%\just-snapshot\scroll-debug\`. Every long-capture session then writes `first.png`, each distinct sampled frame and `log.txt` (target program, window class, DPI, wheel events, stitch results) into a timestamped subfolder (`scroll_dump.rs`). Replay one with `SNAPSHOT_SCROLL_REPLAY=<folder>` and the test binary `replay_dump --ignored --nocapture`; frames that do not match print the best shift and where the rows still differ. Delete the folder to turn recording off.

## Release Flow

1. Bump `version` in `Cargo.toml`, run `.\snapshot.ps1 build` to sync `Cargo.lock`, write the user-facing notes under `## vX.Y.Z` in `RELEASE_NOTES.md` (Chinese, one `- ` item per change: what users notice, not commit titles), and commit.
2. `git tag vX.Y.Z`, `git push origin HEAD`, `git push origin vX.Y.Z`.
3. In the publishing machine's desktop session (the release key is in its Credential Manager, which remote shells cannot read): `.\snapshot.ps1 release -Tag vX.Y.Z [-KeyId <id>]`. It creates a **draft** with the setup executable, the ZIP, their SHA256 files, the bare `just-snapshot.exe` and the signed `latest.json`, with the notes as the release text. It refuses to run on a dirty tree, without notes for the version, when the remote tag is not at `HEAD`, when the key is missing or not in `TRUSTED_KEYS`, or when a release for the tag already exists.
4. A human reviews and publishes the draft on GitHub. Do not tag, push, or publish unless asked. Installed copies see the update once the release is published (not a draft, not a prerelease): they read `releases/latest/download/latest.json`.

Release keys: one ECDSA P-256 key per publishing machine, created there with `.\snapshot.ps1 release-key [-KeyId <id>]` (default id: the computer name). The private key stays in that machine's Credential Manager (`just-snapshot/release-key/<id>`); its public key goes into `TRUSTED_KEYS` in `src/release_key.rs`. A new machine can publish only after a release containing its key, published from a machine that is already trusted. To retire a machine, remove its key and release. Never copy or export a private key.

## UI Conventions

The overlay follows Snipaste's layout:

- The main toolbar is centered directly below the selection. If it does not fit, it goes above; if neither fits (a full-screen selection), it goes inside the selection's bottom edge.
- Toolbar groups: drawing tools | undo, redo | long capture, pin, save, exit, copy. `GROUP_STARTS` in `toolbar.rs` defines the dividers.
- The secondary option bar is centered under the toolbar. It opens downward when the toolbar is below the selection, otherwise upward, so it never covers the selection. It does not follow the text box.
- Panels take their colors from `theme::palette()` and are drawn anti-aliased with GDI+, with a 2 px shadow inside their bounds (`toolbar::SHADOW`). Never hard-code colors in UI code; add a palette field instead.
- Text boxes use Snipaste-style chrome: a 1 px dashed outline, small square corner handles and a rotation knob. Anything painted must stay within the rect that gets invalidated, or it leaves trails.
- Layout changes need matching updates to the unit tests in `toolbar.rs`, `annotation_options.rs`, and `selection/tests/text.rs`.
- Clipboard behavior has an on-demand test against the real clipboard; run it in a desktop session after touching `output.rs`: `<test binary> clipboard --ignored --test-threads=1`.

API keys and other secrets live only in the Credential Manager: never in `translate.txt`, the repo, logs, error messages or command lines. Before every commit, check the file list for anything key-like.

Launch just-snapshot for testing through the shell (`explorer.exe <path to just-snapshot.exe>`), never as a direct child of a packaged (MSIX) app such as the Codex desktop app. A child of a packaged app inherits its package identity, so its `%LOCALAPPDATA%` and `HKCU` writes go into the package's private store (`%LOCALAPPDATA%\Packages\<package>\LocalCache\...`): the settings it saves are invisible to a normal launch and the start-at-login entry never reaches the real `Run` key.

A capture hotkey conflict must never stop the app or open a modal dialog. The tray icon switches to the warning badge, the tooltip names the conflict, one non-modal notification is shown (clicking it opens settings), and the tray menu gets a "change shortcut" item. Registration is retried whenever the tray menu or settings opens. Saving an occupied shortcut is allowed; the settings window shows the conflict live before saving.

## Settings Window

- Everything is painted in `Painter`; `Layout` owns every rect so painting and hit testing agree. Add new controls to `Layout::targets`.
- Sizes are 96-DPI constants multiplied by the window's DPI scale; fonts are recreated on `WM_DPICHANGED`.
- Animations run on one 15 ms timer that stops when everything settles. Do not add idle timers.
- Colors: accent for primary actions, amber for warnings (conflicts, duplicates), red only for errors. The window is frameless: the header is the drag area and has its own close button.
- Errors go through `show_error`, which opens the themed dialog in `dialog.rs`; do not call `MessageBoxW`.
- Error text shown to the user is never cut off: no `DT_END_ELLIPSIS`, no height caps. Wrap with `DT_WORDBREAK | DT_EDITCONTROL` so paths break mid-word; the dialog scrolls a message taller than the screen. A one-line area (like the settings footer) shows a short summary and sends the full error to `show_error`.

## Text Editing and Change Visibility

- Use `apply_patch` for ordinary text and source-code edits. Preserve the original encoding and line endings. If `apply_patch` cannot safely preserve them, use a narrowly scoped alternative and explain why.
- If no change card is visible, identify the modified files and summarize the changes in the final response.

## Temporary Files

- Keep temporary AI scripts, probes, screenshots, and verification output outside the repository, under a task-specific directory in the system temporary directory.
- Exclude `AI_Temp/` and temporary artifacts from staging, commits, and submission lists.

## File Deletion

- When deleting files or directories with PowerShell, do not pass `-Force` to `Remove-Item`.
